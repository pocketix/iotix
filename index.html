IoTiX Project Overview

IoTiX is a block- and form-based visual programming language and editor currently being developed by Petr John and Jiří Hynek at BUT FIT, primarily aimed at automating smart devices on mobile phones.

The first prototype was created through a collaboration between BUT FIT and Logimic as part of the project Services for Water Management and Monitoring Systems in Retention Basins.

More information is available on the Pocketix GitHub Organization.

IoTiX specifically refers to the current ecosystem of editors and interpreter built around the first version of the IoTiX scripting language.

Getting the Source

The iotix repository bundles the editors and the interpreter as git submodules:

git clone --recurse-submodules https://github.com/pocketix/iotix.git
cd iotix
# if you cloned without --recurse-submodules:
git submodule update --init --recursive

Editors (React or Angular)

cd iotix-react        # or: cd iotixng
npm run install:all
npm run start:demo    # starts a local dev server with the demo application

The Angular demo is served at http://localhost:4200; the React demo prints its URL when it starts. npm run build:lib builds only the reusable editor library and npm run build:demo produces a production build of the demo.

Interpreter

cd iotix-node
npm install           # also compiles TypeScript to dist/ (postinstall)
npm run test

The packages are also published to the GitHub Packages registry as @pocketix/iotix-node and @pocketix/iotix-react. To install them into another project, point the @pocketix scope at that registry in your .npmrc (GitHub Packages requires an access token with read:packages):

@pocketix:registry=https://npm.pkg.github.com

Docker

Both editor repositories contain a multi-stage Dockerfile that builds the demo on node:20-alpine and serves it with nginx on port 80:

cd iotix-react        # or: cd iotixng
docker build -t iotix-editor .
docker run -p 8080:80 iotix-editor

IoTiX Editor (React & Angular)

The IoTiX Editor, available in React and Angular (pocketix-react and pocketixng respecively) versions, provides mobile interfaces for designing automation flows. These editors are ideal for non-programmers. Key features include block and form-based editing, configurable conditions and actions, device integration and workflow logic, and compatibility with the IoTiX scripting language.

The visual editor is composed of several integrated components that collectively support both graphical and textual programming. At its core, the Program module manages synchronization between the text and visual editors while maintaining an undo history. The Text Editor enables direct user input and ensures real-time updates to the graphical view, whereas the Visual Editor facilitates intuitive visual programming through recursively nested blocks, commands, and expressions. To enhance adaptability, the system supports Dynamic Language Modification, allowing runtime changes to accommodate diverse device models. Finally, Input Validation ensures correctness through syntactic checks in the text editor and semantic validation in the graphical interface.

IoTiX Interpreter

The IoTiX Interpreter, is built around two core interfaces, IReferenceManager and ICommander, which abstract system-specific details and enable integration with diverse environments, including those with custom digital twins or non-JavaScript runtimes. IReferenceManager manages loading and storing of device parameters, while ICommander handles the dispatching of execution commands. Program execution begins with the creation of a ProgramRunner, which parses the program into an Abstract Syntax Tree (AST) and constructs a dependency table. Each block in the program can be evaluated and visually represented, ensuring alignment between graphical and textual logic. The evaluation process involves retrieving parameters, binding values, traversing the AST, and dispatching the resulting commands through the provided interfaces.

Through this architecture, the IoTiX Interpreter provides a powerful backend for executing IoTiX scripts, enabling consistent and adaptable automation across smart environments.

Usage & API

Program Format

Programs are JSON. A program is an object with a block array of statements. Compound statements (if, else, while, fork, ...) carry a condition expression and a nested block; commands carry params. The same structure exists in two forms:

  • Readable form: produced and consumed by the editors. Commands and references use the names defined by the language, e.g. PowerStrip.1 or Water Level.lvl_measurement_percent_full.
  • Serialized form: accepted by the interpreter. Commands are named deviceId.commandId.commandValue and references deviceId.parameter, where deviceId and commandId are numeric.

Converting between the two is the responsibility of the system that embeds the editor, because only it knows which device and command a name refers to. Before running a program it replaces names with ids; afterwards it maps the returned commands back to names for display. Neither the editors nor the interpreter perform this mapping. The demo applications show one way to do it (capabilityAndVariablesReplacers.ts in each editor's demo). A program in serialized form:

{
  "block": [
    {
      "name": "if",
      "condition": "hours(now) > 14 && hours(now) < 23",
      "block": [
        { "name": "5451.56.close", "params": [] }
      ]
    },
    { "name": "write", "params": ["5451.temperature", "21"] }
  ]
}

Like the other statements, a parameter write is identified by its name: write with the params [reference, value]. The value is stored as given, without evaluation.

The available statements, their forms and icons are not hard-coded: each editor receives a language definition at runtime, which is what enables Dynamic Language Modification.

Embedding the Editor

React (@pocketix/iotix-react) exports the IotixEditor component together with defaultSettings, capabilityTemplate and the settings types:

import {IotixEditor} from '@pocketix/iotix-react';

<IotixEditor language={language}
             program={program}
             level={0}
             onProgramChange={(changed) => setProgram(changed)}
             settings={settings}      // optional, defaults to defaultSettings
             menu={<MyButtons/>} />  // optional, extra menu items

Angular (iotixng) provides IotixVpModule; its root component is <iotix-vp-program>:

<iotix-vp-program
    [language]="language"
    [program]="program"
    [settings]="settings"
    (onProgramChange)="onProgramChange($event)">
  <div menu><!-- optional extra menu items --></div>
</iotix-vp-program>

Interpreter API

@pocketix/iotix-node exports ProgramRunner, ProgramRunnerError, ICommander, IReferenceManager, ReferencedValue, Command, Program and ValueType. To integrate it, implement the two interfaces and subclass ReferencedValue for your device parameters:

interface ICommander {
  // Receives the commands produced by evaluation; dry === true means "do not actuate".
  sendCommands(dry: boolean, commands: Command[]): Promise<void>;
}

interface IReferenceManager {
  // Loads current values of the device parameters the program references.
  load(references: {parameterName: string; deviceId: number}[]): Promise<ReferencedValue[]>;
  // Persists parameters that the program changed (write statements).
  store(references: ReferencedValue[]): Promise<void>;
}

Then parse and run a program:

import {ProgramRunner, ProgramRunnerError} from '@pocketix/iotix-node';

const runner = new ProgramRunner()
    .setCommander(commander)
    .setReferenceManager(referenceManager)
    .parseProgram(program);           // serialized form, after the host's name-to-id conversion

try {
  const {commands, toUpdate} = await runner.run(/* dry = */ false);
} catch (e) {
  if (e instanceof ProgramRunnerError) {
    console.error(e.phase, e.cause); // 'parse' | 'load' | 'evaluate' | 'sendCommands' | 'store'
  }
}

run(dry) loads the referenced parameters through IReferenceManager.load, evaluates the program, passes the resulting commands and the dry flag to ICommander.sendCommands, stores changed parameters through IReferenceManager.store, and returns both lists. The interpreter works only with this digital twin and never communicates with devices: delivering the commands to the devices and persisting state is the job of the system above IoTiX, reached through your ICommander and IReferenceManager implementations. That system also decides whether a command is executed at all, so ignoring commands when dry is true gives a safe simulation mode. Every failure is rethrown as a ProgramRunnerError whose phase identifies the failing step.
